# extract: 결정 추출

- 검증: 사전 프로토타입으로 3턴 세션에서 확인(결정 12, 인용 19/19 일치)
- 모델: sonnet
- 입력(표준 입력): 세션 압축 텍스트. 형식은 아래 "입력 형식"
- 출력: [contracts.md](../contracts.md) 2.3의 extract 스키마
- 변경 이력: v0.1 수락한 결정이 코드 근거만 달려 AI 단독으로 오분류 → 처음 등장한 발화를 첫 근거로. v0.2 AI가 덧붙인 예외가 사람 지시에 묻힘 → 별도 결정으로 분리. 규칙 전문은 [설계서](../design.md) 5.6

## 지시문 (이 블록 안만 `claude -p`에 넘긴다)

```text
너는 개발 대화 기록에서 '코드에 영향을 준 결정'을 뽑는 분석기다.
표준 입력으로 Claude Code 개발 세션을 압축한 기록이 주어진다.
- [m:xxxx|user] 사용자 발화, [m:xxxx|assistant] AI 발화
- [e:N|edit 경로 +추가/-삭제] AI가 파일에 쓴 코드 (추가된 줄만)

규칙:
1. 코드의 동작이나 구조에 영향을 준 결정만 뽑는다. 진행 보고, 인사, 도구 사용 설명은 제외한다.
2. 결정마다 근거(evidence)를 1~3개 단다. ref는 기록의 표식(m:... 또는 e:...)을 그대로 쓰고,
   text는 그 항목의 원문을 글자 그대로 10~200자 복사한다. 요약하거나 고쳐 쓰거나 말줄임표를 넣지 않는다.
3. 결정이 대화에서 처음 등장한 발화(제안, 지시, 질문)를 반드시 첫 번째 근거로 단다.
   사용자가 지시했다면 그 사용자 발화를, AI가 제안했다면 그 AI 발화를 인용한다.
   대화에서 전혀 언급되지 않고 코드에만 나타난 결정(AI가 말없이 넣은 처리)일 때만 e: 항목의 코드 줄을 첫 근거로 쓴다.
4. reason은 근거로 인용한 항목에 실제로 나온 이유만 쓰고, 없으면 "기록에 근거 없음"이라고 쓴다.
   사용자가 수락했는지 같은 경위는 reason에 쓰지 않는다.
5. alternatives에는 기록에서 실제로 언급되었거나 버려진 대안만 쓴다. 없으면 빈 배열.
6. level: 인터페이스, 데이터 모델, 모듈 책임, 예외 계약 같은 구조는 structure, 함수 내부 처리는 implementation.
7. related_symbols에는 결정이 반영된 함수나 클래스 이름을 쓴다. 메서드는 Class.method 형식.
8. 같은 결정을 중복해서 뽑지 않는다. 대화 중에 바뀐 결정은 최종 결정만 뽑고, 바뀌기 전 내용은 alternatives에 넣는다.
9. 사용자 지시를 구현하면서 AI가 스스로 덧붙인 예외, 조건, 기본값은 사용자 지시와 합치지 말고 별도 결정으로 뽑는다.
   그 결정의 첫 근거는 AI가 그 내용을 처음 말한 발화(없으면 코드)로 한다.
summary와 reason은 한국어 한 문장으로 쓴다.
```

## 입력 형식

> **구현 참고용. 프롬프트에 넣지 않는다(few-shot 예시로 붙이지 말 것).** 모델에는 위 "지시문" 블록 안만 넘긴다.

- 발화: `[m:<uuid 앞 8자리>|user] 텍스트`, `[m:<uuid 앞 8자리>|assistant] 텍스트`
- 편집: 첫 줄 `[e:<번호>|edit <상대 경로> +<추가>/-<삭제>]`, 다음 줄부터 추가된 줄(최대 60줄, 넘으면 `... (N줄 생략)`)
- 항목 사이 빈 줄 하나. 40,000자 단위로 나누고 앞 덩어리의 마지막 발화 2개를 겹쳐 넣는다(편집은 겹치지 않음)
