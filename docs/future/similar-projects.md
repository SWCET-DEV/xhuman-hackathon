## "comprehension-check"는 어느 리포인가

이름 검색 결과 중 **agharsallah/comprehension-check**로 판단했다. 설명이 "Claude Code mod: after every code change, Claude quizzes you"이고, 우리 기획서 7장 표와 참고문헌도 이 리포를 링크한다. 나머지 동명 리포는 일본어 빈칸 학습 앱, 강좌 과제 제출용, 이탈리아어 교육용 스킬(Samuel88/code-comprehension-check-skill, 학생에게 코드베이스 질문) 등으로 범위가 다르다.

## 프로젝트별 비판적 메모

### RonaldSit/comprehension-debt
- README는 "3 questions about YOUR file"이라고 하지만 실제 질문은 `repay.py`의 `_template_questions`가 만든다. 첫 질문만 가장 복잡한 함수의 첫 분기를 끼워 넣고, 나머지 둘은 "무엇을 고려하고 버렸나", "가장 덜 명백한 가정은"으로 **어느 파일에나 같은 문장**이다. 분기가 없으면 질문은 2개다. `--llm`을 줘도 질문은 바뀌지 않는다.
- LLM 채점은 "1~5점, 엄격하게, 코드와 대조" 수준의 총점 지시이고 루브릭이 없다. 휴리스틱은 길이와 파일 고유 식별자 포함 여부로 점수를 준다. 한국어 답변은 식별자가 적어 불리하다.
- "BugsInPy 버그 파일 93% 상위 사분위"는 부채 점수(위험 순위)의 근거이지 질문·채점의 타당성 근거가 아니다.
- 기준이 명확한가: 우선순위 공식은 명확하다. 질문과 채점 기준은 우리보다 약하다.

### Adityakk9031/cdebt
- 셋 중 채점 기준이 가장 명확하고 객관적이다. 정답이 실행으로 정해지고, 통과선이 코드(`adaptive.py`의 `required_correct`, `require_hard`)에 박혀 있다. 질문 기각 규칙도 명시적이다: 답이 질문에 들어 있으면, 해시·난수 값이면, 실행 전에 실패하면, 출력이 불안정하면 버린다.
- 대가는 범위다. 묻는 것은 "이 함수가 이 입력에 무엇을 반환하나" 같은 **추적 능력**이지 "왜 이렇게 했나"가 아니다. 자체 사례에서 내장 생성기는 AI 작성 함수 565개 중 1개만 퀴즈로 만들 수 있었고(에이전트 추가 시 41개), 외부 Python 리포 3곳에서도 3문항 이상 만들 수 있는 함수는 36~49%였다.
- 스스로 "거짓말 탐지기가 아니다", "개인이 아니라 코드를 측정한다"고 적는다. 기록 파일은 로컬에서 위조 가능하다고도 밝힌다.
- README의 "함수당 3문항, 2/3 통과"와 `adaptive.py` 독스트링의 "3~5문항, 기본 4"가 어긋나 보이지만, 정책 기본값은 3이라 README가 맞다.

### agharsallah/comprehension-check
- 우리와 가장 가까운 것은 질문 규칙이다. `hooks/prompts/quiz/rules.ts`가 "사용자가 요청하지 않은 Claude의 결정(기본값, 가정, 범위에서 뺀 것, 충돌하는 요구를 어떻게 풀었는지)을 최소 1문항 묻는다", "테스트를 추가하거나 돌렸다면 그것이 무엇을 증명하고 무엇을 놓치는지 묻는다", "가장 위험한 부분부터"를 요구한다. 트리아지 프롬프트도 "올바른 동작에 대한 결정을 담은 테스트"를 퀴즈 대상으로 본다.
- 이 도구는 세션 안에서 돌아서 Claude가 대화 맥락을 안다. 즉 "사용자가 요청하지 않은 결정"을 구분할 정보는 있다. 다만 원문 인용 검증, 포괄 수락과 보류의 구분, 함수별 누적 기록과 순위는 없다.
- 채점은 코드를 쓴 그 Claude가 자기 변경에 대한 퀴즈를 내고 직접 채점한다(서브에이전트 모드면 `answer_key`를 먼저 쓰게 함). 루브릭은 "핵심 아이디어가 있으면 correct, 일부면 partial, 이유가 틀린 정답 선택은 partial". 통과선이나 "이해했음" 기록은 없고 학습용 점수판이다.
- 채점 규칙 중 "사용자 답이 정답 키가 놓친 것을 보여 주면 사용자가 맞다"는 우리에게 없는 규칙이다.

## 우리와 겹치는 점

- 이해 부채라는 문제 설정, 위험도 기반 우선순위, 소수 문항 퀴즈 → 설명 → 기록이라는 흐름. 세 곳 모두 있다.
- "질문 3개"는 RonaldSit(파일당 최대 3)와 Adityakk9031(함수당 3)에 이미 있다.
- "AI가 사람이 요청하지 않고 정한 것을 묻는다"는 agharsallah에 프롬프트 규칙으로 있다. 우리 결정 주체 중 "AI 단독"과 겹친다.
- "테스트가 무엇을 막는지/놓치는지 묻는다"도 agharsallah에 있다. 우리 테스트 변경 질문은 "AI가 기존 테스트의 기대값을 바꿨을 때"로 더 좁고 구체적이지만, 독자적이라고 말할 수준은 아니다.
- 채점을 "정답 아이디어 충족 여부"로 보는 것 자체는 agharsallah의 core idea 채점과 비슷하다. 차이는 포인트로 쪼개고 상태를 프로그램이 계산한다는 점이다.

## 우리가 다른 점

### 발표에서 말해도 되는 것
1. **질문의 출발점이 대화 원문의 결정이다.** 결정을 원문 인용과 함께 추출하고, 원문과 일치한 인용만 근거로 쓴다. 세 곳 중 대화 원문을 근거로 검증하는 곳은 없다(코드 확인 기준).
2. **"누가 정했는가"로 순서를 정한다.** 특히 "나중에 정하자"고 했는데 코드에 들어간 보류 후 반영, "좋아"로 넘긴 포괄 수락을 구분해 가중치를 준다. agharsallah는 "요청 안 한 결정"을 묻기만 하고 구분·가중·누적은 하지 않는다.
3. **채점에서 AI가 총점을 매기지 않는다.** AI는 포인트별 충족만 보고 이해/부분/모름은 프로그램이 정한다. RonaldSit(LLM 1~5점)·agharsallah(LLM이 문항 판정)보다 판정 근거가 쪼개져 있고 재현성을 따로 잴 수 있다.
4. **놓친 포인트만 설명하고 다른 상황으로 다시 묻는다.** 비슷한 재질문은 Adityakk9031에도 있지만 목적이 다르다(붙여넣기 의심 시 시간 제한 추가 질문).

### 말하면 안 되는 것
- "최초", "유일", "대화를 보는 유일한 도구". agharsallah는 세션 맥락을 본다.
- 퀴즈·상환·만료·위험 점수·질문 3개를 차별점으로 내세우는 것. 모두 이미 있다.
- "AI가 채점하지 않는다", "객관적 채점". 객관성은 실행 기반인 Adityakk9031가 우리보다 확실히 강하다. 우리는 포인트 충족을 여전히 AI가 판정한다.
- "검증된 채점", "정확도 95%". 실측은 답변 15개에 포인트 84%, 판정 75%이고 답변도 Claude가 썼다.
- "이해를 증명한다", "AI 붙여넣기를 잡는다". 세 곳 모두 이를 못 한다고 밝히고 있고 우리도 마찬가지다.
- "테스트 변경 질문은 우리만 한다".

## 기획서·Q&A 문서에서 고칠 표현(리포는 손대지 않음, 발표에서 말로 보정)

1. **두 프로젝트 모두 CLI 이름이 `cdebt`다.** RonaldSit도 `pip install comprehension-debt` 후 `cdebt scan`으로 쓴다. qa-prep.md 39행 예상 질문 "cdebt도 질문 3개, 3분 상환, 만료가 있던데"는 RonaldSit(질문 3개·3분)와 Adityakk9031(해시 만료)를 섞었다. 심사위원이 "cdebt"라고 하면 어느 쪽인지 되묻거나 둘 다 답한다.
2. proposal.md 84행 "파일당 질문 3개"는 사실상 템플릿 질문 2~3개이고, 그중 둘은 모든 파일에 같은 문장이다. 우리 질문이 "결정마다 다르게 생성된다"는 점의 근거가 된다. 단 우리 질문이 실행마다 달라지는 약점과 맞물리니 과장하지 않는다.
3. qa-prep.md 26행 "README에 해시 만료 언급 없음"은 맞지만, VALIDITY.md에 변경량 기반 감쇠가 있다. "만료 없냐"는 질문엔 "해시 만료는 없고 변경량 감쇠는 있다"고 답한다.
4. agharsallah 행에 "테스트가 무엇을 증명·놓치는지 묻는 규칙"도 있다는 점을 알고 있어야 한다.

## 구현 범위를 바꾸지 않고 참고할 만한 것

## 심사위원이 "이미 있는 것 아니냐"고 물을 때

> 네, 이해 부채를 재고 퀴즈로 확인하는 오픈소스는 여러 개 있고 저희도 확인했습니다. Adityakk9031의 cdebt는 코드를 실행해서 정답을 확정하기 때문에 "이 함수가 무엇을 반환하나"는 저희보다 객관적으로 채점합니다. 대신 "왜 이렇게 했나"는 실행으로 답이 안 나와서 묻지 못합니다. comprehension-check는 Claude가 요청받지 않고 정한 것을 묻지만, 그 결정이 대화 어디서 나왔는지 원문으로 확인하지 않고, 기록도 남기지 않습니다. 저희는 대화 원문에서 결정을 꺼내, 사람이 "나중에"로 미뤘거나 "좋아"로 넘겼는데 코드가 된 결정을 먼저 묻습니다. 퀴즈와 상환은 그걸 위한 기본 흐름이지 차별점이 아닙니다.
