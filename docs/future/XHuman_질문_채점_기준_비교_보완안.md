# XHuman 질문·채점 기준 비교 및 보완안

- 확인일: 2026-11-11
- XHuman 기준 커밋: `b530aa804952008c5d3f0b3a84ac2c2e2c7cfcdd`
- 확인 범위: XHuman 문서·프롬프트와 비교 프로젝트의 구현 코드
- 검증 한계: 소스 비교 결과이며, 각 도구의 채점 정확도를 직접 실험한 결과는 아니다.
- 저장소 파일은 수정하지 않았다.

**네 프로젝트 모두 기준은 있다. XHuman도 “AI가 적당히 질문하고 점수를 주는” 수준은 이미 벗어났다. 다만 지금 보완할 핵심은 질문 유형을 늘리는 것보다, ‘정답의 근거’와 ‘통과가 의미하는 범위’를 명확히 하는 것이다.**

## 2. XHuman에서 이미 잘 정해진 부분

현재 문서에는 다음이 명시돼 있다.

- 변수명·상숫값을 외우는 문제보다 **그 결정의 결과와 실패 상황**을 묻는다.
- 결정 이유가 기록에 없으면 **동기를 지어내서 묻지 않는다.**
- 핵심 포인트는 **구체적 사실 하나씩**, 서로 겹치지 않게 만든다.
- 짧거나 표현이 달라도 의미가 같으면 인정한다. 답변에 없는 내용을 추측해서 인정하지 않는다.
- 설명 후에는 같은 질문을 반복하지 않고 **다른 상황에 적용하는 재확인 질문**을 한다.
- AI가 반환한 포인트 번호가 누락·충돌해도 잘못 통과시키지 않도록 프로그램 집계 규칙이 있다.

따라서 Ronald의 길이·식별자 중심 기본 채점을 가져올 필요는 없다. XHuman의 의미별 포인트 채점이 목적에 더 적합하다.

다만 **“AI가 혼자 정한 결정을 묻는다”는 것만으로는 차별점이 부족하다.** comprehension-check도 명시적으로 한다. XHuman의 강점은 **그 결정을 대화 원문에 연결하고, 보류·포괄 수락 같은 사람의 관여 방식으로 질문 우선순위를 정하는 것**이다.

## 3. 해커톤을 위해 보완할 기준 — 우선순위 순

아래는 현행 기능 설명이 아니라 **보완 제안**이다.

| 우선순위 | 현재 빈틈 | 보완할 기준 | 반영 위치 |
|---|---|---|---|
| **1** | 핵심 포인트가 문자열뿐이라 사실의 근거를 추적하기 어려움 | **각 포인트의 근거를 코드 / 대화 기록 / 명시된 외부 가정으로 구분한다.** 코드 동작은 코드로, 당시 결정 이유는 대화로 확인한다. 둘이 다르면 문제에 그 차이를 밝힌다 | `question.md`, 시연 질문 검수표. 장기적으로는 포인트별 근거 필드 |
| **2** | 테스트 질문의 “기대값을 바꾼 것이 맞는 판단인가요?”는 요구사항이 없으면 정답이 정해지지 않음 | **변경 전후 어떤 동작을 허용·차단하는지 먼저 묻는다.** 옳고 그름은 요구사항 근거가 있을 때만 채점한다. 근거가 없으면 판단 보류를 정답으로 인정할 수 있어야 함 | `question.md` 테스트 질문 규칙 |
| **3** | 포인트를 충족했는지만 보면 정답지가 틀린 문제도 채점 가능 | **문항 오류와 개발자의 이해 부족을 구분한다.** 근거 없는 포인트, 질문에 없는 전제, 여러 해석이 가능한 문항은 채점을 보류하고 이해 상태를 갱신하지 않는다 | `contracts.md`, `test-cases.md` |
| **4** | 함수의 가장 최근 질문 하나를 통과하면 해당 단위가 `understood`가 됨 | 현 지표를 **“핵심 질문 통과 단위 비율”**이라고 설명한다. 함수의 모든 동작·결정을 이해했다는 뜻으로 발표하지 않는다. 추후 `decision_id`와 질문을 연결해 확인한 결정만 집계 | `contracts.md`, 리포트·발표 문구 |
| **5** | 질문 품질 규칙은 있지만 실제 생성물이 이를 어기는 사례가 기록됨 | 실시간 검토 AI를 추가하기보다 **개발 중 생성 질문을 고정된 검수 기준으로 검사하고, 별도 답변 세트로 채점 회귀 검증** | `test-cases.md`, C1 검증 절차 |

특히 4번은 문서에 명백히 드러난다. 현재 계약은 질문이 **어느 결정을 물었는지는 기록하지 않는다**고 명시한다. 따라서 같은 함수의 타임아웃 질문을 통과해도 429 처리나 DB 기록까지 이해했다고 볼 근거는 없다.

## 4. 질문과 채점 기준의 구체적 예시

현재 시연 코드에 맞춘 **보완 예시**다.

| 항목 | 제안 |
|---|---|
| 확인하려는 이해 | 타임아웃과 확정 결제 실패를 구분하는가 |
| 질문 | “`timeout=5`를 지정했고 전체 제한 시간도 충분한데 두 번의 호출이 모두 `TimeoutError`로 끝났다면, 이 함수는 어떤 예외로 종료하며 실제 결제가 실패했다고 확정할 수 있나요?” |
| 포인트 0 | 최종적으로 `ChargeOutcomeUnknown`이 발생한다 |
| 포인트 1 | 응답을 받지 못했어도 PG에서 결제가 처리됐을 가능성이 있다 |
| 완전 정답 예 | “결과 불명 예외로 끝납니다. PG에서는 처리됐을 수도 있어서 결제 실패라고 확정할 수 없습니다.” |
| 부분 정답 예 | “결과 불명 예외가 발생합니다.” → 포인트 0만 충족 |
| 오답 예 | “두 번 다 타임아웃이므로 결제는 확실히 실패했습니다.” → 모두 미충족 |
| 채점하지 않을 내용 | 정확한 예외명을 몰라도 ‘결과를 확정할 수 없는 예외’라는 의미가 명확하면 인정. 질문하지 않은 백오프 계산이나 DB 저장 방식은 요구하지 않음 |

근거는 실제 [retry.py](https://github.com/SWCET-DEV/xhuman-hackathon/blob/b530aa804952008c5d3f0b3a84ac2c2e2c7cfcdd/tests/fixtures/demo-payment/payment/retry.py)다.

여기서 **타임아웃을 지정하지 않은 상황과, 호출 후 타임아웃이 발생한 상황을 섞으면 안 된다.** 현재 코드는 `timeout`을 생략하면 PG 호출 전에 `ValueError`가 발생한다. 그 문제의 정답에 “PG에서 이미 결제됐을 수 있다”를 넣으면 정답지 오류다. 질문 생성에서 가장 먼저 잡아야 하는 종류의 오류다.

또한 **현재 코드의 동작을 설명하는 것과 그 동작에 동의하는 것은 다르다.** “현재 코드는 429를 재시도하지 않지만, 요구사항에 따라 바꿔야 한다”는 답을 설계에 반대한다는 이유로 감점하면 안 된다.

## 5. Claude 개발·Codex 검증 역할에 연결하는 방법

Codex가 생성된 질문을 아래 여섯 기준으로 먼저 검수하도록 한다.

1. 질문의 전제가 현재 코드·대화와 일치하는가?
2. 질문에 실제로 답할 수 있을 만큼 조건이 주어졌는가?
3. 핵심 포인트마다 확인 가능한 근거가 있는가?
4. 포인트 하나가 사실 하나이며, 다른 포인트와 중복되지 않는가?
5. 질문하지 않은 내용을 정답의 필수 조건으로 요구하지 않는가?
6. 질문 자체가 정답을 알려 주거나, 근거 없는 동기를 요구하지 않는가?

그다음 **짧은 정답·동의어 정답·부분 정답·그럴듯한 오답·서로 모순되는 답·채점 지시를 삽입한 답**을 섞어 검증한다. Codex와 사람이 기대 판정을 먼저 정하고, 실제 채점 결과를 나중에 비교하는 방식이 좋다. 모델 결과를 보고 정답지를 바꿨다면 그것은 기준 개선용으로 쓰고, 정확도 평가는 새로운 답변으로 해야 한다.

현재 저장소도 15개 답변 검증에서 최초 사람 판정과의 일치가 **포인트 84.0%, 최종 판정 74.7%**였으며, 정답지를 수정한 뒤 나온 높은 수치에는 순환 요소가 있다고 밝힌다. 이는 저장소에 기록된 실측이며 이번에 재현한 수치는 아니다.

근거: [검증 기록](https://github.com/SWCET-DEV/xhuman-hackathon/blob/b530aa804952008c5d3f0b3a84ac2c2e2c7cfcdd/docs/verified-facts.md#L74)

**해커톤에서는 XHuman의 현재 구조를 유지하면서 ‘포인트 근거 확인 → 잘못된 문항은 채점 보류 → 통과 범위 명시’를 우선 보완하는 것을 권한다.** Aditya의 실행 검증 전체를 하루 안에 도입하기보다, 시연 질문의 동작 근거를 실제 테스트로 확인하고 comprehension-check처럼 질문 품질 검증을 별도로 두는 편이 범위에 맞다.
