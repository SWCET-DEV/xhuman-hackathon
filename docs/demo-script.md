# 시연 대본 (3분, 라이브 데모 + 캡처본 백업, 금 11/13)

이 문서는 구현의 완료 기준이다. 아래 명령이 대본대로 끝까지 돌면 구현이 끝난 것이다.

## 0. 발표 방식

- **라이브 데모가 기본이다.** 단, AI 호출은 리플레이 모드(`XHUMAN_REPLAY=1`)로 한다. 프로그램은 실제로 실행되고, AI 응답만 리허설 때 실제로 받아 둔 캐시에서 나온다. 네트워크, 구독 로그인, 응답 편차와 상관없이 같은 화면이 나온다.
- 답변이 미리 정한 문장이라는 점도 3번 장표 작은 글씨로 밝힌다(즉석 답변처럼 연기하지 않는다).
- 발표에서 이 점을 숨기지 않는다. "AI 응답은 리허설 때 받은 실제 응답을 재생합니다. 실시간 호출은 회당 5~15초라 3분 시연에 맞지 않습니다"라고 한 문장으로 말한다. 질문이 오면 `XHUMAN_REPLAY` 없이 한 번 돌려 보일 수 있게 준비한다.
- **백업은 캡처본이다.** 장면마다 터미널과 리포트 화면을 캡처해 슬라이드 뒤쪽에 둔다(아래 4장 목록). PC나 화면 연결이 안 되면 캡처본으로 같은 순서를 설명한다.
- 답변은 `demo_answers.json`의 문장을 그대로 친다(타이핑이 불안하면 `--answers` 옵션으로 파일에서 읽는다). 답변 글자가 다르면 캐시가 맞지 않아 리플레이가 실패한다. `--answers`로 진행할 때의 건너뛰기·상환 규칙은 [contracts.md](contracts.md) 4장 표(Q2만 재확인 답을 넣어 상환).

## 1. 시작 상태 만들기 (발표 직전)

```bash
scripts/demo_reset.sh      # 샘플 코드 git 복구 → 측정 DB만 삭제(캐시는 유지) → XHUMAN_REPLAY=1 ingest. 사전 측정 없음
xh status                  # 아래 "시작 숫자"가 나오는지 확인
```

커버리지 대상(11/10 녹화본 기준, 테스트 파일 제외): `payment/retry.py` 7개 + `payment/store.py` 2개 = 9개. 높음 3개(`charge_with_retry`, `create_payments_table`, `record_payment`, 모두 `payment` 태그, `record_payment`은 `db_write`도), 낮음 6개(예외 클래스 4개와 `__init__` 2개). 가중치 합 = 3×4 + 6×1 = 18.

**사전 측정 없이 시작한다(11/10 발표자 확정).** 낮은 위험 단위를 "이미 이해함"으로 넣으려면 질문 고르기가 우선순위상 그 단위를 고르지 않으므로 상태를 직접 넣어야 하는데, 그건 측정하지 않은 결과를 만드는 일이다. 대신 "위험한 것부터 갚으면 위험 가중 커버리지가 더 빨리 오른다"를 보여 준다.

| 항목 | 숫자 | 계산 |
|---|---|---|
| 시작 단순 / 위험 가중 | 0% / 0% | 0/9, 0/18 |
| 장면 4 뒤 단순 / 위험 가중 | 11% / 22% | `charge_with_retry` understood → 1/9, 4/18 |

버린 대안: 발표 전에 `xh check --unit`(새 옵션)으로 낮음 6개를 실제로 답해 두면 시작 67% / 33% → 장면 4 뒤 78% / 56%. 목요일 작업 약 40분(옵션 구현 + 질문 6개 생성·답변·채점 캐시)이 늘고, "미리 확인해 두었다"고 밝혀야 한다.

계산 규칙은 [contracts.md](contracts.md) 1.2. **슬라이드의 숫자와 화면 숫자가 반드시 같아야 한다.** 녹화 후 실제 단위 목록으로 다시 계산해 이 표를 채운다.

Q1·Q3의 답은 파일에 넣되 재확인 키(`-r`)는 넣지 않아 상환하지 않는다. 그래서 커버리지는 Q2의 `charge_with_retry`만 오른다(Q1은 테스트 단위라 커버리지 밖, Q3은 `unknown`).

테스트 변경 감지를 컷했으면(build-plan 컷 라인 1) 장면 3을 빼고, 그 30초를 장면 2에 준다. 고정 출력을 실제 기능처럼 보이지 않는다.

**녹화 중 관찰(11/10, 2턴 뒤):** AI가 타임아웃을 10초로 넣지 않고 `DEFAULT_TIMEOUT_SECONDS = None` + 값이 없으면 PG를 호출하지 않고 `ValueError`로 정했다. 장면 2의 "10초로 넣어 두었습니다"는 녹화가 끝난 뒤 "제가 미룬 타임아웃을 AI는 '값이 없으면 결제를 막는다'로 정해 뒀습니다"로 바꾸고, 장면 4 질문·`demo_answers`도 실제 질문 생성 결과에 맞춰 다시 쓴다. AI가 스스로 밝힌 임의 결정(주문 필드 가정, 재시도 예외 범위, Retry-After 형식)은 AI 단독 후보. 429 재시도는 1턴 제안에 있어 포괄 수락 후보.

**녹화 후(11/10, 8턴 완료):** 6턴 "4xx는 재시도하지 마"로 409·429 재시도가 함께 사라져 최종 코드는 429를 재시도하지 않는다. 장면 1의 질문을 409로 바꿨다. 최종 코드는 최대 2회, 테스트 43개 통과. 추출 결과와 한계는 [session-script.md](session-script.md) 3장. 장면 2·4와 `demo_answers`는 실제 질문 생성 뒤에 다시 쓴다.

## 5. 질문·채점·상환 실제 실행 결과와 `demo_answers.json` (11/10, 2차)

question-v0.4(sonnet), grade-v0.4·repay-v0.4(haiku)로 녹화본에서 실제로 생성했다. AI가 낸 문장은 고치지 않는다. 답변은 발표자가 미리 정한 문장이고, 이 사실을 3번 장표에 밝힌다.

**질문은 실행할 때마다 달라진다.** 같은 녹화본인데 v0.3에서는 Q2가 "값이 없을 때 결제 상태", v0.4에서는 "5초 타임아웃이 두 번 나면 결제 상태"로 나왔다. 목요일 C1에서 새로 만든 캐시가 다르면 S6에서 대사와 답변을 그 결과에 맞춰 다시 쓴다(결과를 대사에 맞추지 않는다). 아래는 그 작업의 견본이다.

**Q1 테스트 변경** (`test_gives_up_after_exactly_two_attempts_on_transient_failure`, 기대값 3 → 2): 고정 문장. 핵심 포인트
  0. 바뀌기 전 기대값(호출 3회)은 일시적 실패가 나도 재시도를 총 3번까지 하도록 재시도 횟수의 상한을 고정해 두던 장치였다.
  1. 바뀐 기대값(호출 2회)은 재시도를 한 번만 하고 포기해도 통과한다는 뜻으로, 시도 횟수를 3회에서 2회로 줄인 동작을 정상으로 인정한다.
  2. 기대값만 바꾸면 재시도 횟수가 줄어든 것이 의도된 변경인지 버그인지 검증이 사라지고, 일시적 실패를 덜 복구해 ChargeOutcomeUnknown(결제 결과 불명)이 더 자주 발생할 수 있다.
  3. 이 테스트는 AI가 100% 작성했고 위험 태그도 없으므로, 횟수를 2회로 줄이기로 한 근거(요구사항이나 결정 기록)가 있는지 확인되지 않으면 올바른 판단이라고 단정할 수 없다.

**Q2 보류 후 반영** (`charge_with_retry`)

- 질문: "PG 호출 timeout(응답을 기다리는 최대 시간) 기본값을 비워 두기로 미뤄서 호출자가 timeout=5처럼 직접 넘겨야 하는데, 이렇게 넘긴 상태에서 PG가 실제로 결제를 처리하고도 5초 안에 응답하지 못하는 일이 두 번 연속 생기면 이 함수는 어떻게 동작하고, 그때 결제는 어떤 상태일 수 있나요?"
- 핵심 포인트
  0. 첫 번째 타임아웃은 TimeoutError로 잡혀 실패로 확정되지 않고, 대기 후 같은 멱등키(idempotency key, 중복 결제 방지용 키)로 재시도된다.
  1. MAX_ATTEMPTS가 2라 두 번째도 타임아웃이면 시도가 소진되어 ChargeFailed가 아닌 ChargeOutcomeUnknown(결과 불명) 예외가 올라간다.
  2. 이때 PG에서는 결제가 실제로 완료됐을 수도 있으므로 타임아웃이 결제 실패를 뜻하지 않는다.
  3. 재시도가 같은 멱등키를 쓰기 때문에 재시도 자체로 이중 결제가 생기지 않으며, 최종 결제 여부는 호출자가 결제 상태를 따로 조회해 확인해야 알 수 있다.
- 답변(오해: 타임아웃이면 결제 안 됨) → 3회 모두 ①만 충족, partial
- 상환: 흐름 1문장 + 결정 3개(인용 3개 모두 원문 일치)
- 응용 재확인 질문: "timeout=3으로 호출했는데 첫 시도는 연결 오류(ConnectionError), 둘째 시도는 PG가 503을 돌려줬다. 이때 함수가 던지는 예외의 종류, 그 예외를 받은 호출자가 결제 상태를 확인하는 방법, 그리고 두 시도가 같은 멱등키를 쓴 것이 이중 결제 위험에 주는 의미를 설명하라."
- 재확인 답변(설명 문장을 옮기지 않고 다른 상황에 적용) → 3회 모두 understood
